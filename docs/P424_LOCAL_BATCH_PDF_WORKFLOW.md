# P4.24 — Practical multi-document native Hancom PDF conversion (local WSL2)

This is the shortest **usable** path from a directory of HWPX files
to real PDFs generated by the installed Windows Hancom office.

## Run

On Windows 11 with WSL2 and a working local Hancom installation:

```bash
cd ~/ChatGPT-Web-HWPX-MCP-P424-native
source .venv/bin/activate
git pull --ff-only

mkdir -p /mnt/c/p424-validation/batch
python scripts/p424_batch_native_pdf.py \
  "/mnt/c/Users/kimwo/Downloads" \
  --output-dir /mnt/c/p424-validation/batch \
  --recursive --dry-run

# If the preview lists only the documents you intended:
python scripts/p424_batch_native_pdf.py \
  "/mnt/c/Users/kimwo/Downloads" \
  --output-dir /mnt/c/p424-validation/batch \
  --recursive
```

You can also supply one or several explicit `.hwpx` file paths rather
than a directory. No production MCP, signing key, Render service or Docker
is needed for this local conversion lane. The existing
`p424_local_hancom_acceptance.py` and
`p423_wsl_hancom_pdf_bridge.py` do the actual work, invoking Hwp.exe;
the batch module does not introduce another converter.

## Output

Each source has a unique output directory made from its sanitized
filename and hashed absolute source path (so duplicate filenames in
different input directories cannot overwrite each other). Example:

```text
C:\p424-validation\batch\
  p424-batch-report.json
  document-<path-id>\
    document.native-hancom.pdf
    document.p424-acceptance.json
    document.native-hancom.pdf.receipt.json
```

The PDF contains the full original document unless the native Hancom
conversion itself reports failure. The file name and output receipt are
not an indication of independent visual approval.

## Repeat runs

- `CREATED_UNREVIEWED`: A new real Hancom PDF was produced and the
  source/output hashes match the job receipt.
- `REUSED_VERIFIED`: The source SHA, PDF SHA, PDF bytes and PDF signature
  were revalidated against the previous acceptance manifest; **no COM
  work** was repeated. This confirms byte identity, not equation fidelity.
- `BLOCKED_EXISTING_ARTIFACTS`: An old/partial/mismatched artifact
  exists. The script refuses overwrite; use a new output root or manually
  inspect the existing job. It deliberately does not auto-delete files.
- `FAILED`: A specific document failed; other input files continue.
- `WOULD_CREATE`: Dry-run preview; no Hancom call, new PDF, directory
  or report is written.
- `SKIPPED_OUTPUT_TREE`: Input is already inside the output root.

The script writes a JSON batch summary and preserves individual signed
*local bridge* receipts (not P4.14 cryptographic signatures). It never
labels an unreviewed PDF as production approved.

## Verification

```bash
python -m unittest discover -s tests -p 'test_p424_batch_native_pdf.py' -v
python -m unittest discover -s tests -p 'test_p424_*.py' -v
```

The synthetic unit tests cover duplicate names, nested discovery,
source change, corrupted PDF, verified resume, dry-run immutability and
per-document failure isolation. Real Windows/COM validation remains
the owner's earlier successful single-document test; this new batch
entrypoint has not yet been run with real user documents.
